One chip, four ways to read it

A chip designer writes code, a synthesis tool turns it into logic gates, a layout tool turns the gates into transistors, and a fab prints them. Here is a small RISC-V system-on-chip (SoC) taken all the way down. Run a program on it, then pick any line of code, gate, transistor cell or state and see the same thing in every other view.

The chip

A RISC-V core, its memory and eight LEDs

The core runs RV32I, the 32-bit base of the open RISC-V instruction set. This teaching core implements 17 of RV32I’s 40 instructions, with their real 32-bit encodings. It is a multi-cycle design: each instruction takes three to five clock cycles, and a 12-state controller decides what every part of the datapath does in each one. Step through the program and watch the controller and datapath change, cycle by cycle.

        Pipeline
        
    The same program on a five-stage pipeline
    
        
    Real cores overlap instructions: fetch (IF), decode (ID), execute (EX), memory (MEM) and write-back (WB) work on five different instructions at once. Results are forwarded straight from one stage to the next, so most neighbours do not wait. Two things still cost cycles: a load whose result is used by the very next instruction stalls one cycle, and a taken branch throws away the two instructions fetched behind it.
    
      
    
    
    
    
    
    
    
    
    Branches are resolved in EX and the core predicts “not taken”. The multi-cycle numbers come from the same run as the chip above; both cores are checked against a plain instruction-by-instruction run.
    
  
    

  
    
    
    
      05
      
    
        x86 compatibility
        
    Running x86 code on a RISC-V core
    
        
    x86 instructions are 1 to 15 bytes long and many touch memory and the flags register at once. Modern x86 chips do not execute them directly: the decoder first finds where each instruction ends, then splits it into simple micro-operations (µops) that look a lot like RISC-V instructions. A binary translator does the same job in software. Below, real x86 machine code is length-decoded, split into µops and translated into RV32I, then run on the core above.

    Why x86 has flags and RISC-V does not
    Every x86 add, subtract or compare writes the flags register (zero, sign, carry, overflow), and a later jump reads it. RISC-V has no flags: its branches compare two registers directly. The translator here keeps flags “lazily”: it only remembers which result the zero flag depends on, and turns dec ecx; jne into one bne. x86 chips do the same pairing in hardware, fusing a compare and the jump after it into one µop.
    
      
    What a real translator adds
    All the other flags (carry, overflow, sign), 8- and 16-bit registers, the SIB addressing byte, prefixes, string instructions, precise exceptions and self-modifying code. Hardware also needs a microcode engine for the rare complex instructions. That is why x86 front ends are big, and why a fixed 4-byte RISC-V instruction is cheap to decode.
    
      
    Register map
    eax → x10, ecx → x11, edx → x12, ebx → x13, esp → x2 (the stack pointer), ebp → x8, esi → x14, edi → x15. x5 holds loaded operands.
    
    
    
  
    

  
    
    
    
      06
      
    
        What the models leave out
        
    A real SoC is a million times bigger
    
      
    
    
    
    
      
      
    • Only two blocks reach gates and layout: a 4-bit ALU slice and the controller. The register file, memory and bus stay at the RTL and block level. A real 32-bit ALU would also use a faster carry scheme than this ripple carry.
      • 
      
    • The layout is placement only. Wires are not routed: a real flow adds metal routing, buffers, a clock tree, power straps and fill, and checks the result against design rules.
      • 
      
    • Timing uses logical effort with unit-sized cells and no wire load. It gives delays in τ and FO4 (one FO4 is about 5 τ), not picoseconds, and the tool never resizes a gate to speed up the critical path.
      • 
      
    • Synthesis is two-level Quine–McCluskey with shared product terms. Commercial tools restructure logic over many levels, and the state encoding is fixed at binary here.
      • 
      
    • The core has no interrupts, exceptions, privileged mode, caches, multiply or shifts. The x86 decoder knows 14 mnemonics (54 one-byte opcodes) in 32-bit mode, with no prefixes, keeps only the zero flag, and its µop counts are a typical split that varies from core to core.
      • 
      
    • The FinFET and nanosheet cells use the estimated pitches of the Gate to silicon bench, not a foundry library.
