# v1.11 plan, grilled

Hard questions on the v1.11 plan, asked before writing code, with the answer we committed to. Written 3 November 2026. HANDOFF.md was not available in this session; where an answer depends on one of its sections, it says so.

## 1. The rename

**Why rename at all, and why now?** The project's centre has moved from "history of the transistor" to "how transistors are made". The name should say so before the Fab Journey and process theaters ship, not after people have linked to them.

**What breaks?** Four things:
1. **GitHub Pages.** GitHub forwards the old repository and git URLs after `gh repo rename`, but it does not forward a project Pages site. Every link to the old site address 404s. *Answer:* ship a "we moved" page that also forwards deep links (`docs/moved/`), and tell Alek the trade-off: publishing it in a new repository with the old name stops GitHub forwarding the old repository URL.
2. **Text inside images.** The banner, the link-preview image and all 25 README GIFs had the old name drawn into their pixels. *Answer:* the banner and preview image now render from `scripts/banner.html`, and every GIF is re-recorded from the live pages by `make gifs`.
3. **The setup script.** Run with the new name before the repository is renamed, v1.10's script would have created a second, empty repository. *Answer:* the script now renames the old repository if it finds it.
4. **Things nobody remembers.** *Answer:* a test (`tests/test_rename.py`) fails if the old slug appears anywhere except CHANGELOG.md and a line that says "formerly".

**What stays?** Chapter files, data, models and history. Only names and links change.

## 2. The size budget

**How much room is left?** v1.10's zip was 27,782,617 bytes. The limit is 30 MiB (31,457,280 bytes), so 3.67 MB of headroom, about 13 %.

**What filled it?** The README animations: 25 GIFs, 16.9 MB uncompressed, and GIFs barely compress further in a zip. One GIF (`circuit_zoom.gif`, 3.1 MB) was twice the 1.5 MB rule.

**What will grow next?** Process theaters are code and JSON (small); photos are hot-linked from Commons (zero bytes). The risks are more GIFs, PDF manuals and screenshots.

**Rules we adopt:**
- Each GIF at most 1.5 MB, enforced by `tests/test_budget.py`; the four largest are re-encoded with every other frame and a smaller palette.
- The zip must stay under 28 MiB (2 MiB of headroom kept for the next release); hard limit 30 MiB.
- Per-folder ceilings in `tests/test_budget.py`, so growth has to be a conscious edit.
- Generated PDFs (manuals) are built by CI and published on Pages, not shipped in the zip.
- QA screenshots (`qa-out/`) and `dist/` are never zipped.
- Next lever if needed: `figures/` keeps both PNG and SVG of every chart; the README could use SVG only.

## 3. The process-theater format

**What is one theater, concretely?** One record in `data/fab_steps.json` plus one ES module. The record is the single source of truth; the page, the Fab Journey, the Virtual Fab and the printed manual all read it.

**Required fields:** problem it solved and when (with a reference), how it works, the model that simulates it (Python file and JavaScript twin, or `null` until one exists), recipe ranges, metrology, failure modes, photos (by candidate id), timeline (each event cited), safety tier, and Beginner / Engineer / Process engineer text.

**What stops invented numbers?** A recipe range can only exist with a reference key that resolves, and `min <= max` with a unit. Until a source is checked the range stays empty and `needs_source` says which source to read. `tests/test_fab_steps.py` enforces this.

**What about dangerous chemistry?** Safety tier 3 steps (for example the wet cleans that use hydrofluoric acid and piranha) may not carry any recipe at all; the test enforces it. Tier meanings in the seed are a working guess and need reconciling with HANDOFF.md §9.4.

**What does every theater have to pass before it ships?** Twin parity test, 390 px with no overflow, keyboard scrubber, aria-label on every canvas, reduced-motion still frame, and "What the models leave out".

## 4. The Virtual Fab

**What is it modelling?** A one-dimensional and then two-dimensional stack of layers, changed by step operations (grow, deposit, pattern, etch, implant, anneal, polish). The same rules run in Python and JavaScript.

**How does it know an order is wrong?** From the `requires` graph in `fab_steps.json` (tested to have no cycles) plus physical checks, such as implanting with no mask, or etching with nothing patterned.

**Yield and cost, without inventing numbers?** Yield uses the existing Poisson, Murphy and negative-binomial models (`yieldcost.py`, cited). Per-step costs are not public, so cost is shown as wafer price (cited, `fab_economics.json`) spread over the step count, clearly labelled as a teaching estimate and not a foundry cost.

**Scope for the first version:** the 4–6 mask teaching CMOS track only. GAA and backside power come after the cross-section engine is proven.

## 5. Photo licensing

**What may we use?** Public domain, CC0, CC BY and CC BY-SA only, or written permission logged in `data/images.json`. No non-commercial or no-derivatives licences, since the site is CC BY.

**Hot-link or mirror?** Hot-link Commons (keeps the zip small); the Pages workflow mirrors best-effort.

**Equipment-maker photos?** Press images from ASML, Applied Materials, Lam, Tokyo Electron and KLA are all-rights-reserved. Excluded unless permission is written and logged.

**US government images?** Work by federal employees (for example NIST, NASA) is public domain. Images from contractor-run national laboratories are not automatically public domain; check each one.

**How is a candidate checked?** `scripts/check_photo_licenses.py` reads the licence and author from the Commons API and marks each candidate verified, rejected or missing. Only verified ones move to `images.json`. This session could not reach Commons, so all 23 candidates are still "unverified".
